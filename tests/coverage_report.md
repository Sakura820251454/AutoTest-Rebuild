1. **`executor` 结果判读与断点续测**（最高优先）：用合成 `summary.csv` 覆盖 `_read_case_result`、`_collect_results`、`_find_last_completed_batch`，包括"Success/Fail 混合""中途缺行""第二批续跑"三种场景。无需硬件。**（已于第二轮补齐，见第七节）**
2. **`generator` 工程生成**：临时目录造一个最小模板，验证 `generate` / `_generate_from_template` / `_replace_project_name` 产出的文件树与工程名替换结果。无需 CCS。**（已于第二轮补齐，见第七节）**
3. **`MainWindow` offscreen 冒烟**：构造主窗口、断言关键控件存在、触发开始/停止槽函数不抛异常。成本最低、收益直接。
4. **`pipeline_worker` 阶段编排**：mock 三个执行器，验证 generate→build→test 顺序、失败即止、`stop` 生效。
5. **`config` 非法参数分支**：参数化覆盖线程数/超时/成功失败关键字/跨盘符路径，顺手把 `src\` 行覆盖率推到 95% 以上。

## 五、结论：当前自动化够不够挡住常见回归

- **能挡住的部分**：配置读写与新旧格式、路径解析（源码/冻结双模式）、用例配置生成、executor 后处理（剥 CCS 头、FLASH 加密去重、工程复制）、FLASH 加解密、报表 2/3 列、GUI 配置面板字段往返、`_config_to_dict` 字段完整性。这些正是历史上真实出过问题的地方，且现已由 107 例守住。
- **挡不住的部分**：**测试结果判读与断点续测**、**工程生成**、**主窗口启动与阶段编排**。这三块是"改完不点就可能坏、坏了还不一定报错"的区域，目前基本没有自动保护（`executor.py` 行覆盖仅 32.1%）。
- **总体判断**：对"配置/路径/后处理"类常见回归，当前自动化**够用**；对"结果判定、工程生成、GUI 启动"类回归**还不够**。建议至少补上第四节第 1、2 项——它们是纯文件操作，不依赖硬件，投入小且正好覆盖风险最高的业务链。
- GUI 分支覆盖率 12.3% 偏低，主要来自大段一次性 UI 构建代码，不必按行数追平；用 offscreen 冒烟覆盖"能启动、能点击"即可。

### 7.3 过程中发现的真实缺陷（已记录，未修改源码）

1. **耗时列非整数会整条丢弃结果**（`src\executor.py` `_read_case_result`）——**已修复**
   - 证据：`summary.csv` 内容 `case1,Success,not-a-number` 时函数返回 `None`，而不是保留 `status=Success`、`duration_ms=None`。对应 `test_unparseable_duration_discards_whole_result`。
   - 原因：`int(parts[2])` 与整个解析逻辑在同一个 `try` 里，`ValueError` 被 `except` 吞掉。
   - 影响：DSS 侧一旦写出 `1.2s`、`12ms` 之类的耗时，已执行的用例会被当作"没有结果"，`_collect_batch_results` 会重试 3 次，最终把批次判为失败，报表里该用例消失或显示失败。属"静默错误结论"。
   - 修复：耗时解析拆到 `_parse_duration_ms`，失败只把耗时置 `None`；回归用例 `test_unparseable_duration_keeps_status`、`test_duration_with_unit_suffix_keeps_status`、`test_empty_duration_keeps_status`、`test_extreme_numeric_durations_do_not_affect_status`。
2. **`_collect_results` 没有生产调用点**（`src\executor.py`）
   - 证据：全仓搜索只有定义处 `925` 与新增测试调用；主流程用的是 `_collect_batch_results`（`run_all` 第 269 行）。
   - 影响：当前是死代码，缺陷不会影响现网；但它有两处静默行为——summary 存在但为空时返回 `[]`，summary 缺少某用例时该用例直接消失（`test_empty_summary_yields_no_results`、`test_incomplete_summary_only_returns_listed_cases`）。若后续有人把它接回主流程，会引入"少了用例却没人报错"的问题。
3. **工程名不做 XML 转义**（`src\generator.py` `_replace_project_name`）——**已修复**
   - 证据：源文件 `a&b.c` 生成成功（`success=True`），但 `.project` 内容为 `<name>a&b</name>`，`xml.etree.ElementTree.parse` 报 `ParseError: not well-formed (invalid token): line 1, column 50`。
   - 影响：工程名含 `&` 时 CCS 导入会失败，而工具侧显示生成成功，排查方向容易被误导。
   - 修复：插入的新工程名按 XML 规则转义（只转义新名字，模板原有实体不二次转义），写入后校验 `.project` 可被 `ET.parse` 解析，失败则 `success=False` 并带 `[E2006]` 错误；回归用例见 `tests\test_generator.py` 的 `ProjectNameEscapingTest`。
4. **替换清单不含通用 `name="..."` 属性**（`src\generator.py`）
   - 证据：补测首轮用 `<project id="..." name="tmpl_proj">` 的合成模板时，`name` 属性未被改写（`<name>`、`<project>`、`artifactName`、`projectName`、`.out/.map/.com.ti` 均正常）。
   - 影响：当前真实模板 `.cproject` 用 `${ProjName}` 宏，暂无实际影响；换模板后可能出现"工程名一半新一半旧"。
5. **跳过被当作成功**（`src\generator.py` `_generate_single`）
   - 证据：目标目录已存在且 `clean=False` 时返回 `success=True`、`error="目录已存在，跳过"`（`test_existing_project_is_skipped_when_clean_false`）。
   - 影响：上层若只看 `success`，会把"没有重新生成"当成"生成成功"，拿到的是旧工程。
